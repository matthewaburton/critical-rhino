# AGENTS.md

Guidance for AI agents working in this repository. `CLAUDE.md` is a symlink to this
file. Read it before changing anything.

## What this is

Critical Rhino is a warm color scheme, dark and light, for Neovim, VS Code and Cursor,
Ghostty, starship, fzf, lazygit and tmux. `palette.toml` is the source of truth: the
scripts in `scripts/` generate every theme from it and check each color against every
surface it's drawn on. The [README](README.md) is for people using the themes;
[`docs/design.md`](docs/design.md) explains every color choice and how each tool's
theme is built. Read the design notes' section for a tool before changing its colors
or its builder.

## Layout

```
palette.toml              the palette: base colors, derived colors, syntax/UI/terminal roles
colors/, lua/             the Neovim plugin; lua/critical-rhino/{dark,light}.lua are generated
extras/<tool>/            every other theme, all generated
docs/design.md            design notes
docs/images/              logo and icons (generated by make logo), screenshots (make screenshots)
scripts/rhino.py          palette loading, contrast minimums, color math, VERSION
scripts/build_<tool>.py   build one theme and check every pair in it
scripts/audit_<target>.py run the real apps and measure what they draw
scripts/preview.py        the site (build/site/), which the release workflow deploys to GitHub Pages
.agents/skills/           agent skills (.claude/skills and .cursor/skills link here)
.github/workflows/        ci.yml (make check on every push), release.yml (on v* tags)
```

## Rules

- **Never hand-edit generated files.** `lua/critical-rhino/{dark,light}.lua`,
  everything in `extras/` and `docs/images/{logo,icon}-*.svg` are generated
  (`.gitattributes` marks them). Change `palette.toml` or the builder, run its make
  target (or `make build`), and commit the source and its output together. `make
  check` fails when a generated file is stale.
- **After changing a rule in `palette.toml`**, run `make derive` to refresh the
  derived hex values it records.
- **Contrast minimums are fixed:** 4.5:1 for text; 3:1 for dim text, marks, the
  cursor and light brights; decoration is exempt. They live in `scripts/rhino.py`.
  When a check fails, change the color or how the tool's roles map onto it. Never
  lower a minimum or drop a pair to make a check pass. When a tool hard-codes a color
  no theme can reach, measure it and list it in the design notes.
- **Standard library only**, Python 3.11 or later. No third-party packages in
  `scripts/`; ruff, installed by `make setup`, is the only development tool.
- **Docs follow the code.** A change to what a theme sets updates that tool's section
  in `docs/design.md`. A new tool follows "Adding a tool" in the design notes and also
  gets a row in the README's "What's included" table, an install section, and a line
  in the layout above if it adds a path.
- **Describe the scheme as it is.** The README, design notes, site and comments
  explain each color by what it does and why it reads, not by how it got there.
- **This repo is public.** No personal paths, email addresses or machine-specific
  settings in committed files. Examples use `~/critical-rhino` and `/home/you`.

## Checks

| Command | Run it |
|---|---|
| `make check` | Before every commit. Every builder's check, the palette check and lint (needs `make setup`) |
| `make nvim:audit` | After changing the Neovim theme. Needs nvim and a lazy.nvim config |
| `make vscode:audit` | After changing the VS Code theme. Needs VS Code or Cursor |
| `make terminal:audit` | After changing terminal colors or the starship, fzf, lazygit or tmux themes. Needs tmux |
| `make screenshots` | After a change that shows in the README's pictures. Slow: runs the terminal and VS Code audits |
| `make site` | To preview the site: open `build/site/index.html` |

`make doctor` reports which tools are installed. CI runs `make check` on every push
without Ghostty or starship; their builders skip what needs the missing tool, so run
`make check` locally too. The audits only run locally.

## Commits

Write commit messages with the `commit-message` skill (`.agents/skills/`). Commit
generated files with the change that produced them. When a change alters a color some
tool draws, say which tools and roles change, and whether it's a palette change (every
tool) or one tool's mapping: release notes are written from those messages.

## Releases

One version covers the whole scheme: `VERSION` in `scripts/rhino.py`. The VS Code
extension and the site take it from there. Numbering:

- **Major:** a file name or install path changes, so people's configs need editing.
- **Minor:** colors change, or a tool is added.
- **Patch:** fixes that change no color (a theme file a tool rejected, docs, scripts).

To release:

1. Set `VERSION`, run `make build` and `make check`, and commit (`Release 0.2.0`).
2. Write the release notes for people using the themes: colors that changed, by tool
   and role; new tools; changed install steps. Make an annotated tag with them,
   keeping Markdown headings: `git tag -a v0.2.0 --cleanup=verbatim -F notes.md`.
3. The maintainer pushes the commit and the tag: `git push origin main v0.2.0`.
   Agents never push.
4. The maintainer uploads the release's `.vsix` to Open VSX: drag it onto the
   **Publish** button at open-vsx.org. This step goes away once Open VSX trusts the
   workflow (below).

The release workflow checks again, refuses a tag that isn't annotated or doesn't
match `VERSION`, creates the GitHub release with the tag's notes and the `.vsix`
attached, deploys the site to GitHub Pages, and publishes the same `.vsix` to the
Visual Studio Marketplace. The site changes only on a release.

Publishing stores no token. The Marketplace publisher `matthewaburton` has a Trusted
Publishing policy for `release.yml` in the `publish` environment, which allows only
`v*` tags; the `marketplace` job exchanges GitHub's OIDC token for a short-lived
Marketplace one. Open VSX offers the same once its `matthewaburton` namespace has a
verified owner: register `release.yml` and `publish` there, then add a job that runs
`npx ovsx publish --trusted-publishing` on the release's `.vsix`. If a store refuses
a version, fix it and re-run the failed job; a version that's already up is skipped.
